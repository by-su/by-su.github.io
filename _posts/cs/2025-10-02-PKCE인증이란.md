## PCKE등장 배경
전통적인 OAuth 2.0의 '승인 코드 승인 흐름(Authorization Code Grant Flow)'에서는 클라이언트(앱)가 사용자의 로그인을 요청하고, 인증 서버로부터 승인 코드를 받아옵니다. 그 후, 클라이언트는 자신의 ID와 비밀번호(Client Secret)를 함께 제시하며 승인 코드를 액세스 토큰으로 교환합니다.

하지만 모바일 앱이나 웹 브라우저에서 실행되는 자바스크립트 앱(SPA)과 같은 공개 클라이언트는 소스 코드가 노출되기 쉬워 Client Secret을 안전하게 보관하기가 사실상 불가능합니다. 만약 공격자가 이 환경에서 Client Secret 없이 승인 코드만 탈취할 수 있다면, 이를 이용해 액세스 토큰을 발급받아 사용자 정보에 접근하는 심각한 보안 문제가 발생할 수 있습니다. PKCE는 바로 이 '승인 코드 탈취 공격(Authorization Code Interception Attack)'을 효과적으로 방어하기 위해 등장했습니다.

## 왜 공개 클라이언트는 위험한가?
1. SPA
   - HTML/JS/CSS 번들이 사용자 브라우저에 내려갑니다. 브라우저 개발자 도구에서 누구나 코드를 볼 수 있다.
   - 로컬 저장소 취약성: `localStorage`, `sessionStorage`, `IndexedDB` 등에 저장된 값은 XSS 공격에 취약하다.
2. 모바일:
   - 바이너리 리버스 엔지니어링: 앱은 누구나 다운할 수 있고 APK, IPA를 디컴파일하면 코드, 리소스, 심지어 내장된 시크릿도 추출할 수 있다.

## PKCE 동작 원리
PKCE는 인증 요청마다 일회성의 비밀 키를 동적으로 생성하여 보안을 강화합니다. 전체 과정은 다음과 같이 두 단계의 키 검증을 통해 이루어집니다.

- **`code_verifier`**: 클라이언트(앱)가 생성하는 암호학적으로 안전한 임의의 문자열입니다. 이 값은 토큰을 요청하는 마지막 단계까지 클라이언트 측에만 안전하게 저장됩니다.
- **`code_challenge`**: `code_verifier` 값을 특정 방식(`S256` 해시 등)으로 변환한 값입니다. 이 값은 인증을 요청하는 첫 단계에서 인증 서버로 전송됩니다.


### **인증 흐름**
1. **클라이언트의 키 생성**: 사용자가 로그인을 시도하면, 클라이언트(앱)는 먼저 비밀 문자열인 **`code_verifier`**를 생성합니다. 그리고 이 값을 SHA256 해시 함수 등으로 변환하여 **`code_challenge`**를 만듭니다.

2. **인증 요청 (with `code_challenge`)**: 클라이언트는 사용자를 인증 서버의 로그인 페이지로 보내면서, 생성한 **`code_challenge`**와 변환 방식(`code_challenge_method`, 주로 'S256')을 함께 전달합니다.

3. **승인 코드 발급**: 사용자가 성공적으로 로그인하면, 인증 서버는 이 **`code_challenge`**를 저장하고, 클라이언트에게 짧은 유효시간을 가진 **승인 코드(Authorization Code)**를 발급합니다.

4. **토큰 요청 (with `code_verifier`)**: 클라이언트는 발급받은 **승인 코드**와 함께, 첫 단계에서 생성하고 안전하게 보관해 두었던 원본 비밀 문자열 **`code_verifier`**를 인증 서버에 보냅니다.

5. **서버의 최종 검증**: 인증 서버는 전달받은 `code_verifier`를 저장해 두었던 `code_challenge_method`('S256') 방식으로 변환합니다. 이 변환된 값이 이전에 저장해 두었던 `code_challenge` 값과 일치하는지 확인합니다.
  - **일치하면**, 인증 요청을 보낸 클라이언트가 토큰을 요청하는 클라이언트와 동일하다고 판단하여 **액세스 토큰을 발급**합니다.
  - **불일치하면**, 중간에 승인 코드가 탈취되었을 가능성이 있으므로 요청을 거부하고 토큰을 발급하지 않습니다.
